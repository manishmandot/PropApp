# Web App (Public) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the public PropApp website: a landing page with the methodology and backtest results, a suburb finder, suburb pages (scores, drivers, history, key figures, map, sources), compare, and a map explorer. It is fast, indexable, and refreshed after every scoring run.

**Architecture:**
- **Database:** a migration adds an `api` schema of read-only views over the scoring and pipeline tables, plus a `web_reader` role that can read only those views.
- **App:** a Next.js App Router app in `web/` reads them on the server with the `postgres` client. Pages are statically generated and refreshed on a timer (ISR), and a scoring run can trigger an immediate refresh through a secret endpoint.
- **Map:** the map explorer draws suburb boundaries from a PMTiles file that the pipeline builds after each scoring run. The file carries only a 5-band score; exact values come from the server when a user hovers.
- **Plans:** every plan check goes through one `entitlements` module that returns "everything visible" until sub-project 4.

**Tech Stack:** Node 22, Next.js 15 (App Router, TypeScript strict), React 19, Tailwind CSS 4, `postgres` (postgres.js) 3, `maplibre-gl` 5 and `pmtiles` 4, Vitest, Playwright, ESLint. On the pipeline side: Python and `tippecanoe` for tiles.

**Spec:** `docs/superpowers/specs/2026-09-29-propapp-design.md` (§6 as revised for this scope, §5.4 for score outputs, and §5.6 for disclaimers). This plan builds on the merged pipeline (`pipeline/`) and scoring engine (`pipeline/src/propapp_pipeline/scoring/`).

## Global Constraints

- **Scope:** pages 1–5 of spec §6.2 only. No sign-in, watchlists, saved searches, alerts, account pages or plan limits; those are sub-project 4. Every page and API route that shows score data calls `getEntitlements()` so that sub-project 4 has a single place to switch limits on.
- **Data access:**
  - The app reads only `api.*` views, as the database role `web_reader`, from server code (server components and route handlers).
  - No database access happens in the browser, and nothing is exposed through Supabase's REST API.
  - All SQL is parameterised with postgres.js tagged templates. The only exception is `ORDER BY` columns, which are chosen from a fixed allow-list.
- **Current model:** the model version of the latest successful `score_runs` row. Every view is limited to it.
- **Suburb URL:** `/suburb/<sal_code>-<name-slug>-<state>`, lower-case, e.g. `/suburb/10060-paddington-nsw`.
  - Slug: the name with any parenthetical removed, then non-alphanumerics collapsed to `-`.
  - A URL whose code matches but whose slug is wrong redirects (308) to the canonical URL. An unknown code gives a 404.
- **Refreshing:** suburb, landing, finder and compare pages use `revalidate = 86400`. `POST /api/revalidate` with `Authorization: Bearer $REVALIDATE_SECRET` revalidates the whole site layout; any other request gets a 401.
- **Score bands (map):** 1 for 0–20, 2 for 20–40, 3 for 40–60, 4 for 60–80, 5 for 80–100 (upper bound inclusive in the top band), and 0 when there's no score.
- **Stale banner:** shown when any source's latest successful ingestion is older than 1.5 × its `cadence_days`, or when it has never succeeded.
- **Missing market layer reason:**
  - "No market data for this state yet" when no suburb in the state has a market score.
  - Otherwise: "Fewer than 20 sales in the last 12 months, or no recent sales data".
- **Disclaimer:** "PropApp scores are general information only, not financial product advice. They do not consider your objectives, financial situation or needs." It appears in the footer of every page, with a longer version on the landing page.
- **Formatting:** prices as `A$1.25m` / `A$850k`, percentages to 1 decimal place, scores as whole numbers.
- **Secrets:** environment variables only (`DATABASE_URL` for `web_reader`, `REVALIDATE_SECRET`, `NEXT_PUBLIC_TILES_URL`, `NEXT_PUBLIC_SITE_URL`). Never committed.

## Review Focus

1. **A fresh deploy with no scores yet.** Expected: every page renders with a "Scores are being prepared" state. There's no 500, the sitemap is empty but valid, and the map shows boundaries without colour. Tests: Task 4 `queries return empty on an unscored database`, Task 11 e2e `empty database renders`.
2. **Suburbs rated `fundamentals` or `insufficient`.** Expected: the suburb page hides the market section and shows the missing-market reason. `insufficient` shows "Not enough data to score" and no numbers. Test: Task 7 e2e `coverage states render`.
3. **Bad URLs.** An unknown code gives a 404, a wrong slug redirects to the canonical URL, and a malformed segment gives a 404. Test: Task 3 `parseSuburbParam`, Task 7 e2e `canonical redirect`.
4. **Hostile or invalid finder parameters** (non-numeric, min > max, unknown sort, a huge page number). Expected: these are ignored or clamped to valid values, never passed into SQL, and never cause a 500. Test: Task 6 `parseFilters`.
5. **Stale or missing sources.** Expected: the banner shows on every page and each suburb page lists every source's last refresh and attribution. Test: Task 4 `freshness flags overdue source`, Task 11 e2e `stale banner`.

  - CLI: `python -m propapp_pipeline build-tiles`, which needs all three pipeline secrets.
